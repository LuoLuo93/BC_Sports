## 1. 背景与目标

六个 Excel 导入服务（BasFirstAdd、GoodsOldNew、EstimatedCost、SalesBudgetFillDaily、
OdsSalesMain、StickerData，外加 StickerSizeGroup 部分沾边）各自维护一份约 300~500 行的导入实现，
其中约 120~150 行流程骨架是逐字拷贝（F09 修 OOM 时"修一处漏五处"即为例证）。
导入日志同样每服务一套：7 张结构完全相同的日志表散布在 2 个库里（6 张主库、1 张企微库），7 份 `saveImportLog`、
7 个 `logPage` 接口、7 处前端日志弹窗。

**目标：**
1. 新增一个导入 = 只写一个 `ExcelImportSpec`（表头别名 + 行映射 + 入库回调，约 40~60 行），流程骨架零拷贝；
2. 修改导入行为（熔断参数/错误上限/读取策略/日志字段）= 只改引擎一处；
3. 导入日志统一：一张表、一个写入器、一个查询服务（7 个瘦接口各挂原有权限）、一个前端组件；
4. 对外行为不变：接口响应 JSON、错误文案、状态语义、各模块日志页数据连续可查、**用户查看日志的权限不变**。

## 3. 目标架构

```
Controller                     引擎（唯一流程骨架）                差异点（Spec，每模块一份）
─────────                      ────────────────────              ─────────────────────────
POST /import  ──►  ExcelImportRunner.run(file, spec)
                   ├─ detectFormat 魔数探测（六份拷贝并入 ExcelSaxUtils）
                   ├─ ExcelSaxUtils.readAllSheets（复用 F09）
                   ├─ row 0 表头识别（spec.headerAlias()）
                   ├─ 逐行：spec.mapRow(RowCtx) → T
                   │        行级 try/catch 计错、MAX_ROWS 熔断
                   ├─ 缓冲满 batchSize → spec.onBatch(batch, ctx)
                   │        （各服务自己的 Mapper + 自己的短事务）
                   ├─ 收尾 flush / fail 截断 / 状态计算
                   ├─ ImportLogRecorder.record(type, outcome, file)   ← 统一日志，主库一张表
                   └─ return ImportOutcome ──► buildResult 兼容旧 JSON
```

职责切分一句话：**引擎管流程，Spec 管差异，入库留在各服务的 Mapper，日志全系统一张表。**

## 4. 设计细节

### 4.1 导入引擎（新包 `com.bcsport.admin.importer`）

```java
/** 全部差异点的声明处，每个导入模块实现一个 Spring Bean（或 lambda） */
public interface ExcelImportSpec<T> {
    String logLabel();                                   // 日志/日志表模块标识用
    ImportType type();                                   // 统一日志模块枚举（见 4.2）
    Map<String, String> headerAlias();                   // 表头别名→字段名
    T mapRow(RowCtx ctx) throws Exception;               // 行映射（cells+columnIndex+工具方法）
    void onBatch(List<T> batch, BatchCtx ctx);           // 入库策略差异点（自己开短事务）
    default String dedupKey(T entity) { return null; }   // 非空则文件内去重保留最后一条（BasFirstAdd 用）
    default int batchSize() { return 500; }              // SQL Server 2100 参数上限按列数自定
    default int maxRows()  { return 2_000_000; }
}

/** 行上下文：rowNum + columnIndex + cellStr/cellInt/cellBigDecimal/parseDate 等工具 */
public final class RowCtx { ... }

/** 批上下文：success.addAndGet(n)、errors.add(...) 记录通道 */
public interface BatchCtx { ... }

/** 统一结果：替代六份 buildResult */
public final class ImportOutcome {
    int total; int success; int fail; List<String> errors; String status;
    // toResultMap() 保持 {total, success, fail, errors} 的 LinkedHashMap 顺序不变
}

/** Spring Bean（需注入 ImportLogRecorder），各导入服务 @Autowired 后调用 */
@Component
public class ExcelImportRunner {
    public <T> ImportOutcome run(MultipartFile file, ExcelImportSpec<T> spec) throws Exception;
}
```

关键机制：
- **行级错误文案约定**：`mapRow` 抛 `IllegalArgumentException` 视为业务校验失败，引擎拼成
  `第N行：<message>`（与现有"第N行：客户id不能为空"逐字一致）；其他异常拼成 `第N行：解析异常 - <message>`。
  `NumberFormatException` 虽是 IAE 子类但按解析异常处理（否则用户会看到裸 JDK 文案）。
  `mapRow` 返回 null 表示静默跳过该行（不计入 total）。
- **去重钩子**：`dedupKey` 非空时，同 key 在**同一未 flush 缓冲内**保留最后一条；每次 flush 清空去重集
  （与现状 `batchIds.clear()` 一致，跨批同 key 由 MERGE upsert 兜底）。
- **两段式适配**（EstimatedCost/StickerData）：`onBatch` 只往自己内存清单攒，读完后在服务方法里
  做存在性检查 + 分批写。两段式的特殊性被关在各自 40 行回调里，不污染引擎。
- **日志自动写**：`run()` 收尾调用 `ImportLogRecorder.record(spec.type(), outcome, file)`，
  try/catch 静默失败（与现状一致，日志失败不影响导入结果）。七份 `saveImportLog` 全部删除。
- **错误上限**固化为引擎常量：行级错误 100 条、批入库错误 200 条（与现状一致），
  fail>100 时追加"…共 N 条未导入，仅显示前 100 条"。
- **xls 分支静默停**、**多 sheet 第一个有效表头生效**等语义全部固化在引擎，带单测。

### 4.2 统一导入日志（主库一张表）

**现状核实（2026-09-09，按 Mapper 所在数据源包判定）**：7 张里 **6 张已在主库 Oracle**，仅
`Bas_FirstAdd_ImportLog` 一张在企微 SQL Server。**"统一日志"实质 = 6 张同库归并 + 1 张从企微库搬入**，
比最初按实体包名误判的"4 库混布"简单得多。

**已确认（2026-09-09 用户拍板）**：旧日志无应用外读取方，仅项目内查询 → 采用方案 A；4.4 备选仅存档。

**选主库的理由**（依然成立）：
1. 日志本质是"管理后台的操作记录"，不是业务库的数据；
2. 现状 7 处 `saveImportLog` 全是导入结束后的独立 insert + try/catch 静默，**与业务数据本来就不在一个事务**，写主库不损失任何原子性；
3. main 包下的 Mapper（`com.bcsport.admin.mapper.**`）任何服务可直接注入，不碰 qywx 等事务管理器；
4. 附带收益：业务库不可用导致导入失败时，主库仍能记一条 FAILED（现状此场景连日志都写不进）。

**表名**沿用主库 `BC_SPORTS_` 前缀惯例：`BC_SPORTS_SYS_IMPORT_LOG`（同 BC_SPORTS_SYS_MENU /
BC_SPORTS_GOODS_IMPORT_LOG；列风格照抄 goods_data_schema.sql：小写列名、IDENTITY 主键、TIMESTAMP）。

DDL（`sql/create_sys_import_log.sql`，幂等，含 IDENTITY 首插验证与搬迁按钮权限）：

```sql
CREATE TABLE BC_SPORTS_SYS_IMPORT_LOG (
    id             NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    import_type    VARCHAR2(40 CHAR) NOT NULL,  -- 模块标识，见 ImportType 枚举
    file_name      VARCHAR2(500 CHAR),          -- CHAR 语义：中文文件名按字符计长，避免 BYTE 语义撞列宽丢整行日志
    file_size      NUMBER,
    total_count    NUMBER DEFAULT 0,
    success_count  NUMBER DEFAULT 0,
    fail_count     NUMBER DEFAULT 0,
    status         VARCHAR2(20 CHAR),           -- SUCCESS / PARTIAL / FAILED
    error_msg      CLOB,
    create_time    TIMESTAMP DEFAULT SYSTIMESTAMP,
    create_by      VARCHAR2(50 CHAR),
    legacy_id      NUMBER                       -- 历史搬迁来源行 ID，新写入为 NULL
);
CREATE INDEX idx_bcs_import_log_type_time ON BC_SPORTS_SYS_IMPORT_LOG (import_type, create_time);
```

三个必须注意的设计点：
1. **搬迁幂等键必须用函数式唯一索引**，不能用普通 `(import_type, legacy_id)` 唯一索引——
   Oracle 复合唯一键把 NULL 视为相等，同模块第二条新记录（legacy_id 全为 NULL）就会撞约束：
   ```sql
   CREATE UNIQUE INDEX uk_bcs_import_log_legacy ON BC_SPORTS_SYS_IMPORT_LOG
     (CASE WHEN legacy_id IS NULL THEN NULL ELSE import_type END, legacy_id);
   ```
   新记录两键全 NULL 不进索引、不受约束；搬迁行按 (type, legacy_id) 防重。
2. **日志页查询排序按 create_time 倒序**（现各 logPage 按 ID 倒序）——搬迁行 ID 大于切换后新行，
   按 ID 排旧历史会浮到最上面。
3. 实体必须显式 `@TableId(type = IdType.AUTO)`——主库 GlobalConfig 默认 ASSIGN_ID 雪花，
   不显式声明会把雪花值写进 IDENTITY 列导致序列漂移（本项目踩过：fix_identity_columns_ora00001.sql）。
   建表后脚本内做一次 IDENTITY 首插验证。

搬迁接口权限：`system:import-log:migrate`，按钮挂「操作日志」(SYS_LOG) 菜单下、授权超管角色，
随建表脚本给齐（照 agent_print_permission.sql 模板）。

> 注意：项目此前踩过 Oracle IDENTITY 序列不同步的坑（fix_identity_columns_ora00001.sql、
> fix_sequences_final.sql）。建表后按既有脚本模式验证一次 IDENTITY 起点，避免首条插入 ORA-00001。

### 4.3 查询接口与前端（与 F70 合并落地）

**写入模型：一次导入只写一行、只写一张表（统一表 BC_SPORTS_SYS_IMPORT_LOG），不双写。**
某模块切换上线后，它的旧日志表即刻停写、应用也不再读它（该模块日志页改读统一表按 type 过滤）；
旧表仅作为搬迁核对与回退的安全网静置一个版本周期后 DROP。不双写的原因：双写等于把 R01 要消灭的
7 套写日志代码原样留下；而回退单个服务（revert 该提交）只会让该服务切换窗口内写入统一表的少量日志
在旧页面不可见，可接受。"用户看的日志表"与"统一表"是同一张，各模块页面只是它的一个 type 过滤视图。

**各模块原有日志查询不变**：7 个既有 `import-log/page` 接口**路径、分页参数、返回字段不变**
（fileName/fileSize/totalCount/successCount/failCount/status/errorMsg/createBy/createTime/id，
仅多出 `importType` 一个字段），内部改读 `BC_SPORTS_SYS_IMPORT_LOG` 并固定各自 type 过滤、按 createTime 倒序。
前端在阶段 1/2 **零改动**。

**权限模型不变——谁能导入谁就能看该模块日志，不是"只有管理员能看"。**
7 个模块日志接口**永久保留**，各自沿用现有 `@RequiresPermissions`（如 first-add 用 `bi:first-add:import`），
只是瘦成一行、全部委托给共享的 `ImportLogService.page(type, pageQuery)`。**不做**"一个泛型接口 + 参数传 type"：
那样要么得新增全局权限（普通用户看不了）、要么得在代码里维护 type→权限映射做程序化校验，
且有跨模块泄露风险（只有 first-add 权限的人查到贴纸日志）。新增导入照旧加一行瘦接口挂自己的权限。

终态（前端可独立排期）：
- 前端抽 `ImportLogDialog` 组件 + `useImportLog.js`（即 F70 的 composable），7 个导入页全部换用，
  各自传自己的日志 API 函数；bi.js/qywx.js/sticker.js 里 7 个日志 API 函数保留（各一行）。
- 唯一管理员专属的是**一次性历史搬迁按钮**（见下文），与"看日志"无关，阶段 4 清理时一并删除。

**历史数据：由应用自身完成一次性搬迁，日志页历史连续可查。**
6 张主库旧表虽可直接 INSERT…SELECT，但企微库那张跨实例不行；为只维护一套机制，7 张统一走应用搬迁器。
新增管理员专用接口 `POST /api/import-log/migrate-legacy`（权限 `system:import-log:migrate`），
逐个读 7 张旧表（复用现有 7 个旧 Mapper 的 selectList，日志表量级仅千行）插入 `BC_SPORTS_SYS_IMPORT_LOG`，
`legacy_id` 记来源行 ID，靠 4.2 的函数式唯一索引**幂等可重复执行**（重复行 DuplicateKey 忽略，返回各模块
"复制/跳过"计数）。执行节奏：切换前跑一次、每个模块切完再跑一次、阶段 3 收尾再扫一次——中间没有空窗。
**旧导入日志处置（2026-09-09 定）：代码删干净，表缓删。**
- **代码**：各服务的 `saveImportLog` 随该服务迁移时删；7 个旧实体 + 7 个旧 Mapper + 搬迁器 + 搬迁接口/权限
  **必须等生产收尾搬迁核对通过后**在独立的"阶段 4 清理提交"里一起删（搬迁器依赖旧 Mapper 读旧表，不能先删）。
  不保留任何常驻的搬迁入口。
- **表**：旧 7 张表保留只读**一个版本周期**作安全网（零成本、DROP 不可逆、不与切换同批上线）。
  DROP 前核对：每模块 `新表 legacy_id 非空行数 == 旧表总行数` + 抽样比对内容；通过后 DBA 执行
  `sql/drop_legacy_import_logs.sql`（含删除搬迁按钮菜单记录）。

### 4.4 备选方案 B（已作废，仅存档）：日志留原库，仅统一代码

若任一旧日志表存在应用外的读取方，则不搬库：`ExcelImportSpec` 增加 `logSink(ImportOutcome, file)`
钩子，各服务把自己旧实体的写入封进 3 行适配器，引擎收尾统一调用。代码重复同样消除、
接口与表零变动、无 DBA 工作；代价是新增导入仍需每次配日志表+实体+Mapper，且跨模块统一日志页无法实现。
两方案引擎部分完全相同，可先按 A 推进，前置确认不过再退回 B，只影响 `ImportLogRecorder` 一个类。

## 6. 分阶段实施（每阶段独立提交、独立验证）

## 7. 行为不变量（验收清单，迁移逐条核对）

- [ ] 响应 JSON `{total, success, fail, errors}` 字段名与顺序不变；
- [ ] 错误文案格式 `第N行：xxx`、MAX_ERRORS=100 截断与"…共 N 条未导入"后缀不变；
- [ ] status 语义：total==0→FAILED、fail==0→SUCCESS、否则 PARTIAL；
- [ ] 每批独立短事务：一批失败丢弃该批不中断整个文件（日志记"批量入库失败"）；
- [ ] 多 sheet：第一个有效表头生效，数据可在任意 sheet；
- [ ] MAX_ROWS 熔断值各模块保持现状（BasFirstAdd/GoodsOldNew/SalesBudget 200 万、
      OdsSalesMain 300 万、EstimatedCost/StickerData 50 万）；
- [ ] BasFirstAdd 文件内去重"保留最后一条"语义不变；
- [ ] EstimatedCost/StickerData 的 Oracle IN 1000 分批与 500/批写入节奏不变；
- [ ] 日志失败不影响导入结果（静默）；
- [ ] 各模块日志查询接口路径/参数/返回字段不变（仅新增 importType）；
- [ ] **各模块日志查看权限不变**：有该模块导入权限即可看该模块日志，普通用户不受任何影响；跨模块不可见；
- [ ] 各模块日志页历史记录连续（搬迁完成后旧记录与新记录同页可见，按 createTime 倒序）。

（现状 OdsSalesMain 记、BasFirstAdd 等不记，统一为记，便于排查"用户说导了但没反应"）。
