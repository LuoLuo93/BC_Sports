# 贴纸打印系统说明

> 更新日期：2026-08-19
> 涉及两个代码库：
> - 后端：`BcSportsDataManageSystem/project`（Spring Boot + MyBatis-Plus，前端打包于 `src/main/resources/static`）
> - 打印代理：`E:\work\BC_Sport\StickerPrintAgent`（C# WinForms，.NET Framework 4.7.2，部署在各仓库打印电脑）

## 1. 系统概览

贴纸打印实现「申请 → 审核 → 下发 → 本地打印 → 回报」的全链路。管理后台只负责单据与任务管理，**实际打印由部署在仓库电脑上的 Agent 程序调用 BarTender SDK 完成**（服务端不直连打印机）。

```
┌─────────────── 管理后台（浏览器） ───────────────┐
│  贴纸打印单(申请/审核)   品牌模板匹配   字段映射    │
│  Agent 监控(在线状态/任务记录/下发打印/补打)      │
└───────────────┬────────────────────────────────┘
                │ /api/sticker/print/*  /api/print/*  /api/agent/*
┌───────────────▼─────────────── 后端服务 ─────────┐
│ StickerPrintService   申请单状态机                 │
│ PrintTaskService      任务生成/拉取/回报/补打/巡检 │
│ AgentService          Agent 注册与心跳            │
│ DB: sticker_print_order(+detail) / print_task /  │
│     print_agent / sticker_brand_template_match / │
│     print_field_mapping                          │
└───────────────┬────────────────────────────────┘
                │ HTTP 轮询(2s) / 心跳(10s) / 结果回报
┌───────────────▼────────── 仓库电脑 Agent ─────────┐
│ PrintTaskPoller 拉任务 → PrintTaskProcessor 串行队列│
│ → BarTenderPrintService 打开 .btw 模板、解析打印机、 │
│   填充字段、调 BarTender 引擎出纸                    │
│ → ResultReporter 回报 completed/paused/failed      │
└───────────────┬────────────────────────────────┘
                ▼
         Windows 打印机（如 CODEPRINT2 / CODEPRINT3）
```

## 3. 业务流程

### 3.1 申请单（sticker_print_order）

状态机：

```
0 草稿 ──提交──> 1 待审核 ──审核通过──> 2 已审核（可下发打印）
                      └──驳 回─── > 3 已驳回（终态，需重新建单）
```

| 操作 | 前置状态 | 规则 |
|---|---|---|
| 创建/编辑/删除 | 仅 0 草稿 | 编辑时整表重建明细；删除为逻辑删除（`deleted=1`，须走 `deleteById`） |
| 提交 | 仅 0 | → 1 |
| 审核 | 仅 1 | 通过→2 / 驳回→3，记录审核人/时间/备注 |

- 单号规则：`SP + yyyyMMddHHmmss + 3位随机数`。
- 单头可填收货信息（联系人/联系电话/收货地址），三者全空则视为未填；下发打印时会先打一张「首张」收货信息标签。
- 明细货品来自 **ERP 跨库查询**（货号/款号/名称/品牌/尺码条码等）；产地/制造商/联系电话等 ERP 占位常量不入库。
- 矫正尺码：明细优先取 `local_size_name`（按尺码组矫正），为空回退 `size_name`。

### 3.2 下发打印（PrintTaskService.createTasksFromOrder）

入口：`POST /api/print/create-tasks/{orderId}?agentId=xxx`（前端 Agent 监控页选择目标 Agent）。

1. 校验申请单必须 `status=2`（已审核）；
2. **幂等**：该单已存在未完成任务（状态 0/1/4）则拒绝，防重复打印；
3. 逐明细按 `品牌名+品类名` 匹配 `sticker_brand_template_match`（须 `is_active=1`），**任一未配置则整体报错回滚**（不产生半成品任务）；
4. **首张任务**：单头填写了联系人/联系电话/收货地址任一项时，先生成一个「首张」任务——模板取字典 `sticker_first_template` 第一条启用项（未配置则整体报错回滚），打印机沿用第一张明细的品牌匹配（保证同机先后出纸），printData 固定键（与 print_head.btw 数据源一致）：`Receiver/ReceiverPhone/ReceiverAddress/BillNo(申请单号)/Qty(打印总数量=明细数量求和)`，数量 1；先于明细插入，Agent 按 createTime 升序拉取故最先打印。三者全空则不生成；
5. 每条明细生成一个 `print_task`：模板文件名、打印机名（来自模板匹配配置）、printData（按字段映射构建）、同批次 `batch_id`，状态 0，指向所选 agentId。

### 3.3 Agent 拉取与执行

**拉取规则（pullTasks，每 2 秒一次）**：

| 任务状态 | 处理 |
|---|---|
| 0 待打印 | 受**在途上限**约束派发 → 置 1，记录 dispatchTime |
| 4 已暂停 | 续打（换纸后自动恢复），**不消耗重派次数**；与待打印共用派发名额，createTime 更早故 FIFO 优先 |
| 1 打印中 | 超过卡住阈值才重派：阈值 = `stuck-base-minutes(默认3分钟) + printQty × stuck-minutes-per-qty(默认0.02)`；重派最多 `max-redispatch(默认3)` 次，超限判失败（状态3） |

> **在途上限（max-inflight，默认 1）**：该 Agent 未回报的 status=1 任务数达到上限后不再派发新任务，只保留卡住重派救援。Agent 是串行打印且边打边拉，不限量时大批量任务在本地队列排队、排队时间计入卡住阈值，会被误判卡住 → 自动重派 → **重复打印**。限为 1 后派发节奏与打印节奏对齐，dispatchTime≈实际开始打印时刻；大批量任务以 status=0 排队属正常（巡检对在线 Agent 的排队不告警）。
>
> **Agent 端 TaskId 去重（双保险）**：Agent 按 TaskId 记忆已下发任务（保留最近 10000 个），服务端任何形式的重复下发（重派/并发竞态）都会被跳过并记 WARN；仅两种情况放行再次下发——回报 `paused`（换纸续打会重发同一任务）和处理过程抛异常（放行给服务端重派救回）。

> 阈值按打印数量自适应，避免 1000 张的大任务因物理打印耗时而被误判卡住导致重复打印。

**打印执行（BarTenderPrintService）**，串行队列逐个处理：

1. 模板路径安全校验：拒绝路径分隔符/盘符/`..` 穿越，必须落在 `PrintTemplet/` 内，文件必须存在；
2. **打印机解析与切换**（见第 4 章）；
3. 打印数量：`PrintSetup.IdenticalCopiesOfLabel = printQty`（同一标签份数）；
4. 字段填充：printData 逐个 `SubStrings.SetSubString(key, value)`，**字段名对不上只记 WARN 照常打印**（该字段出模板默认值，通常空白）；
5. 出纸后按 BarTender Messages 判定：无 Error → 成功；错误文本命中缺纸关键词（paper/缺纸/断纸/卡纸/manual feed/load paper/insert paper）→ 回报 `paused`；其他 → 回报 `failed`（附真实错误文本）。

**Agent 侧可靠性**：

- 结果回报失败按 1s/2s/4s 指数退避重试 3 次；
- 心跳连续失败 3 次标记离线并自动重注册；
- HealthMonitor 每 30 秒检查轮询/队列/心跳/BarTender 引擎，停了自动拉起（5 次失败后降频为 5 分钟一次）；正常状态心跳日志每小时一条（状态变化由各组件即时记录）；
- **未安装 BarTender 的机器**：引擎启动前先做 COM 预检（BarTender.Application ProgID），未注册则不构造引擎（只记一次 WARN，Agent 保持运行不崩溃——老版本会因半成品 Engine 对象终结时抛异常而静默退出进程），装好 BarTender 后由健康监控自动拉起，无需重启 Agent。

### 3.4 任务状态与回报（print_task.status）

| 状态 | 含义 | 迁移 |
|---|---|---|
| 0 | 待打印 | 下发/补打生成；被 Agent 拉取 → 1 |
| 1 | 打印中 | 拉取/重派时置；回报 completed → 2，failed → 3，paused → 4 |
| 2 | 打印成功 | 终态（可补打） |
| 3 | 打印失败 | 终态；errorMsg 存失败原因（可补打） |
| 4 | 已暂停（断纸/缺纸） | 换纸后 Agent 下次 pull 自动续打 → 1 |

### 3.5 补打（reprintTask）

入口：`POST /api/print/reprint`（body: taskId/agentId/reason）。

- 仅终态任务（2 成功 / 3 失败）可补打；进行中（0/1/4）拒绝；
- 该任务已有未完成补打任务时拒绝，防重复补打；
- 克隆原任务全部打印数据生成新任务（`is_reprint=1`、`source_task_id`、`reprint_reason` 留审计），共享原批次号。

### 3.6 巡检告警（checkStuckTasks）

定时任务 `ticket.task.checkStuck`（ScheduleTaskRegistry 注册，调度周期在「定时任务管理」界面配置），**仅告警不改状态**：

| 告警 | 条件 | 多半原因 |
|---|---|---|
| 待拉取积压 | status=0 超 15 分钟未被拉取 | agentId 配错 / Agent 离线 |
| 派发超时 | status=1 超 `max(60分钟, base×(maxRedispatch+1))` 无回报 | Agent 反复崩溃 |
| 暂停挂起 | status=4 长时间未续打 | 忘换纸 / Agent 未恢复 |

## 4. 打印机分配与切换逻辑

### 4.1 打印机名从哪来

打印机名配置在 **`sticker_brand_template_match.printer_name`**（管理后台「品牌-模板匹配」，按 **品牌+品类** 维度全局一套，支持 Excel 批量导入）。下发时原样写入每条 `print_task.printer_name`，补打任务克隆原名。

> 因此打印机配置是全局的、不区分仓库：主仓配置 CODEPRINT2 时，分仓任务也会带 CODEPRINT2——分仓实际只有 CODEPRINT3 就会找不到打印机。这正是 Agent 端切换逻辑要解决的问题。

### 4.2 Agent 端打印机解析（BarTenderPrintService.ResolvePrinterName）

#### 为什么需要这一步

打印机名是后端按「品牌+品类」全局下发的（见 4.1），Agent 机器上未必装了同名打印机。改造前的行为是直接把任务里的名字塞给 BarTender：

- 设置 `PrintSetup.PrinterName` 时若抛异常，只记一条 WARN 就**静默回落到 .btw 模板里保存的默认打印机**——那是模板作者电脑上的打印机，本机多半也不存在（或者存在但根本不是标签机）；
- 最终在出纸阶段报"打印机无效"，任务置失败，报错信息绕了一圈，现场很难排查。

现在在设置打印机**之前**先做一次本地解析，把"这台机器实际用哪台打印机"变成确定性行为。

#### 触发时机

串行打印队列（PrintTaskProcessor）取出任务后、打开 .btw 模板之前，`PrintInternal` 的第一步就是调用 `ResolvePrinterName(task.PrinterName, out switchNote)`。**每个任务独立解析一次**（一张申请单 10 条明细 = 10 个任务 = 10 次解析，1 分钟内共享打印机列表缓存）。

#### 第一步：获取本机打印机列表

- 数据来源：`System.Drawing.Printing.PrinterSettings.InstalledPrinters`，即 Windows「设置 → 打印机」里看到的完整列表，**包含网络打印机**（名称形如 `\\打印服务器\打印机名`）；
- 列表缓存 1 分钟：枚举打印机在有网络打印机的环境下可能较慢（数百毫秒到秒级），打印本身是串行的，没必要每个任务都实时枚举。副作用是拔插打印机后，最多 1 分钟内仍按旧列表判断；
- 匹配规则：**忽略大小写、忽略首尾空格**——`CODEPRINT2`、`codeprint2`、`" CODEPRINT2 "` 都算同一台；命中后返回系统里的原名（规范掉大小写差异），确保交给 BarTender 的名字与本机注册的完全一致。

#### 判定流程

```
任务带打印机名（printer_name）
  │
  ├─ 为空（品牌模板匹配里打印机没配）──────────────> 不切换，用 .btw 模板默认打印机（维持原行为）
  │
  ├─ 本机存在（忽略大小写/空格比对命中）──────────> 直接使用，并把名字规范成本机原名
  │
  └─ 本机不存在
       │
       ├─ 策略A：配置了 fallbackPrinter
       │    ├─ 备用机在本机存在 ────────────────────> 切换到备用打印机，记 WARN
       │    └─ 备用机也不在本机 ────────────────────> 记 WARN「忽略该配置」，继续策略B
       │
       ├─ 策略B：本机恰好只装一台打印机
       │    ├─ 且不是虚拟打印机 ────────────────────> 自动切换到那台，记 WARN
       │    └─ 是虚拟打印机 ────────────────────────> 不切换（防止标签被"打印"成文件）
       │
       └─ 以上都不满足 ─────────────────────────────> 按原任务打印机名继续（兜底路径，见下）
```

#### 策略A —— 显式备用打印机（fallbackPrinter）

- 优先级最高，配置方法见 4.3；
- 配置的备用打印机**必须在本机存在才生效**——防止配置手误切到另一台不存在的打印机；
- 备用机配置了但本机没有时**不直接放弃**：记 WARN 后继续尝试策略B，配置错误最多降级、不会让打印更糟。

#### 策略B —— 本机唯一打印机自动切换（零配置）

- 触发条件：本机**恰好只装了一台**打印机。"分仓只有一台 CODEPRINT3"就是这种场景，现场什么都不用配；
- 虚拟打印机排除：若这唯一一台是虚拟打印机则不切换，否则标签会被"打印"成 PDF/传真文件而不是出纸。排除名单：`Microsoft Print to PDF`、`Microsoft XPS Document Writer`、`Fax`、`传真`（中文 Windows 上的 Fax 本地化名）、以及一切 `OneNote` 开头的打印机；
- 本机装了**多台**打印机时不自动切——无法确定该用哪台，宁可不猜，交给配置解决。

#### 兜底路径（策略都不满足时）

按原任务打印机名继续交给 BarTender，行为与改造前完全一致：设置打印机失败则回落 .btw 模板默认打印机 → 出纸阶段报错 → 任务置失败（状态 3），BarTender 的原始错误文本会回报到后台 `print_task.error_msg`，可在任务记录里直接看到。

#### 不参与切换的情况

- 任务未指定打印机名（品牌模板匹配里打印机留空）：不切换，仍用 .btw 模板保存的默认打印机；
- 任务打印机名在本机存在：直接用（仅做大小写/空格规范化）。多打印机的主仓完全不受影响，只要任务里的名字是对的，永远不会触发切换。

#### 日志与审计

切换痕迹全部记录在 Agent 本地 `Log/` 目录（托盘「打印记录」窗口可实时查看）：

| 场景 | 级别 | 日志样例 |
|---|---|---|
| 策略A切换 | WARN | `任务打印机 [CODEPRINT2] 本机不存在，已切换到备用打印机 [CODEPRINT3] (任务 xxx, 货号 xxx)` |
| 策略B切换 | WARN | `任务打印机 [CODEPRINT2] 本机不存在，本机仅一台打印机，已自动切换到 [CODEPRINT3] (任务 xxx, 货号 xxx)` |
| 备用机配错 | WARN | `配置的备用打印机 [xxx] 本机也不存在，忽略该配置` |
| 无可切换 | WARN | `任务打印机 [xxx] 本机不存在，且无可用的备用/唯一打印机，仍按任务打印机名尝试` |
| 枚举异常 | WARN | `枚举本机打印机失败，跳过打印机切换检查: ...`（不阻断打印） |

打印结果日志中的打印机名也是**实际使用**的那台，如 `打印成功: 货号 x3 -> CODEPRINT3`。

> 注意：后台 `print_task.printer_name` 存的仍是任务下发时的名字，**不会**被改写成切换后的打印机；且成功回报的 message 后端不落库（见第 10 章）。所以"这单实际是哪台打出来的"以 Agent 本地日志为准。

#### 配置生效时机

- **设置窗口保存**：对 `fallbackPrinter` 立即生效——每个任务打印时实时读取配置，下一个任务就按新值解析，无需重启（serverUrl/agentId/apiKey 等其他配置仍需托盘「重启服务」）；
- **手工编辑 settings.json**：需托盘「重启服务」（重启流程会重读 settings.json）。

#### 端到端示例（分仓只有 CODEPRINT3，任务带的是 CODEPRINT2）

1. 后端下发：品牌模板匹配配置 `printer_name=CODEPRINT2` → `print_task.printer_name=CODEPRINT2`，派给分仓 Agent；
2. Agent 拉到任务，解析：本机打印机列表 = `[CODEPRINT3]`，找不到 CODEPRINT2；
3. 未配置 fallbackPrinter（策略A跳过）→ 本机仅 1 台且非虚拟打印机（策略B命中）→ 判定使用 CODEPRINT3，记一条切换 WARN 日志；
4. BarTender 用 CODEPRINT3 出纸，回报 `completed` → 任务状态置 2（成功）；
5. 后台任务记录里 printer_name 仍是 CODEPRINT2，实际出纸机查 Agent 日志那条 WARN 即可。

### 4.3 备用打印机配置方法

分仓电脑上任选其一：

**方式一：设置界面**（托盘右键 → 设置 → 「备用打印机」填如 `CODEPRINT3` → 保存 → 托盘「重启服务」生效）

**方式二：手工编辑 settings.json**

```json
{
  "serverUrl": "http://10.10.0.25:8080/bcsports",
  "agentId": "PC-002",
  "agentName": "分仓打印机",
  "apiKey": "xxx",
  "fallbackPrinter": "CODEPRINT3"
}
```

改完通过托盘「重启服务」生效（重启会重读 settings.json）。留空/删除该键 = 未配置（仅策略B生效）。

**典型场景**：

| 仓库 | 打印机情况 | 需要配置 | 效果 |
|---|---|---|---|
| 主仓 | CODEPRINT2 + 其他打印机 | 无需配置 | 任务带 CODEPRINT2，本机存在，照常打印 |
| 分仓（只有 1 台） | 仅 CODEPRINT3 | **无需配置**（策略B自动生效） | 任务带 CODEPRINT2 找不到 → 自动切 CODEPRINT3 |
| 分仓（多台，想指定） | CODEPRINT3 + 其他 | 配 `fallbackPrinter: "CODEPRINT3"` | 找不到任务打印机时切到 CODEPRINT3 |

## 5. 模板与字段映射

### 5.1 模板（.btw）

- 文件放在 Agent 目录 `PrintTemplet/` 下，**文件名 = 品牌模板匹配里配置的 templateName**（不能带路径）；
- 模板由 BarTender Designer 维护，SubString（命名数据源）名称与下表一致（**区分大小写**）。

### 5.2 数据字段

printData 由 `print_field_mapping`（字段映射，全局单套）构建；未配置映射时使用内置默认映射：

| 模板 SubString 名 | 来源 | 说明 |
|---|---|---|
| MaterialNumber / MaterialName | 明细 | 货号 / 商品名称 |
| StyleNumber / Color / BrandName / KindName | 明细 | 款号 / 颜色 / 品牌 / 品类 |
| SizeName | localSizeName ?? sizeName | 矫正尺码优先 |
| SafetyCategory | 明细 safety_category | 安全类别（选货时从 ERP M_PRODUCT.SAFETY_CATEGORY 快照） |
| EAN13 / Barcode | 明细 | 商品条码 |
| Price | 明细（可配 `.2f` 格式化） | 价格 |
| 其余（执行标准/面料/检验员等） | 映射扩展 | dbField 为空时取 defaultValue 固定值；取不到值也回退默认值 |

> ⚠️ **字段名对不上不会报错、照常出纸**，该字段打出来是空白，仅 Agent 本地日志可见（`部分字段模板未匹配，仍继续打印`，并附模板实际具名数据源列表）。EAN13/Price 等关键字段上线前务必逐项核对。

### 5.3 配置入口

- 品牌-模板匹配：管理后台页面维护，或 Excel 导入（以「品牌名+品类名」为业务键 upsert；品牌/类别反查 ERP M_DIM；模板名需存在于字典 `sticker_template`）。
- 字段映射：管理后台「打印字段映射」页面。

## 7. Agent 配置参考

### settings.json（每台机器一份，设置窗口可改，优先级高于 App.config）

| 键 | 说明 |
|---|---|
| serverUrl | 后端地址，如 `http://10.10.0.25:8080/bcsports` |
| agentId | 本机唯一标识（任务按它派发，配错则任务永远拉不走） |

| 键 | 默认 | 说明 |
|---|---|---|
| TemplateDir | PrintTemplet | 模板目录 |
| LogDir / LogRetentionDays | Log / 30 | 日志目录与保留天数 |
| PollInterval | 2000ms | 拉任务间隔 |
| HeartbeatInterval / HeartbeatFailThreshold | 10000ms / 3 | 心跳间隔/离线阈值 |
| ReconnectInterval | 10000ms | 注册重试间隔 |
| MaxRetry | 3 | 结果回报重试次数 |
| HttpTimeoutSeconds | 10 | HTTP 超时 |
| AckEndpoint | 空 | 配置后拉到任务即发 ack（当前默认未启用） |
| FallbackPrinter | 空 | 备用打印机的 App.config 回退配置 |

### 后端可调参数（application.yml，`agent.task.*`）

| 键 | 默认 | 说明 |
|---|---|---|
| stuck-base-minutes | 3 | 卡住判定基础分钟数 |
| stuck-minutes-per-qty | 0.02 | 每张追加分钟数 |
| max-redispatch | 3 | 最大重派次数 |
| max-inflight | 1 | 在途任务上限（见 3.3，防大批量排队误判重派） |

### 部署要点

1. 目标电脑需 .NET Framework 4.7.2+、BarTender 2016+（已激活）、Seagull 打印机驱动；
2. 复制 Agent 发布目录，首次运行弹设置窗口（取消则退出，避免无配置幽灵进程）；
3. `.btw` 模板放 `PrintTemplet/`；
4. 单实例互斥（Mutex），重复启动会提示；服务方式部署可用 NSSM（进程级自愈）+ 内置 HealthMonitor（组件级自愈）双保险。

## 9. 常见问题排查

| 现象 | 排查方向 |
|---|---|
| 任务一直是 0 待打印 | agentId 配错（巡检日志「未被拉取」告警）；Agent 离线（Agent 监控页看心跳）；后端不可达 |
| 打印失败，error_msg 含打印机错误 | 打印机名本机不存在 → 看是否触发切换日志；多打印机仓库配 `fallbackPrinter`；或检查打印机脱机/缺驱动 |
| 打印失败，error_msg 含模板错误 | `PrintTemplet/` 缺文件或文件名与配置不一致；模板路径非法 |
| 标签出来但字段空白 | 模板 SubString 名与映射不一致（看 Agent 日志「部分字段模板未匹配」及具名数据源列表） |
| 任务停在 4 已暂停 | 打印机缺纸/断纸，换纸后自动续打；长时间未恢复查 Agent 是否在线 |
| Agent 运行一段时间后自动退出 | 未装 BarTender 的机器上，老版本 Engine 构造失败遗留的半成品对象在 GC 终结时抛异常，终结器线程未捕获异常会终止进程（日志表现为"非 UI 线程未捕获异常: 未能加载 Interop.BarTender"）；新版已加预检，未装只记一次 WARN 并保持运行 |
| 打了重复标签 | 自动重复已由在途上限(3.3)与 Agent TaskId 去重拦截；仍出现时多半是「回报丢失→任务被判失败→人工补打」造成——补打前核对 Agent 本地日志确认是否实际出纸；确认单实例运行 |
| Agent 改了配置不生效 | 托盘「重启服务」（会重读 settings.json 并重建 HttpClient） |

日志位置：Agent 本机 `Log/` 目录（可「打印记录」窗口实时看）；后端 `logs/`。

## 10. 已知限制与改进建议

1. **成功回报的 message 不落库**：后端 `reportResult` 对 completed 会 `setErrorMsg(null)`，Agent 侧的"已切换打印机"等信息只在 Agent 本地日志可见。若要后台可查，需后端在 completed 时保留 message 或新增字段。
2. **print_agent.printers 仅注册时刷新**：打印机增删后需重启 Agent（或重连）才更新列表；心跳不携带打印机信息。
3. **Ack 未默认启用**：Agent 的 AckEndpoint 为空，防重复下发依赖 pull 的状态翻转 + 幂等校验 + 在途上限 + Agent 端 TaskId 去重，四层兜底。
4. 打印机切换策略目前是 Agent 端行为，`print_agent.printers` 已具备按 Agent 展示真实打印机的能力，后续如需"按仓库配置打印机"，可在后端做 agent 维度的打印机覆盖配置，下发时改写 printer_name。
5. **大批量任务的排队误判与重复打印风险（已修复）**：曾存在"pull 每轮派发 10 个 + Agent 边打边拉无背压 → 排队任务超过卡住阈值被误重派 → 重复打印；重派超限误标失败后再被真实回报覆盖"。现已双管齐下：① 服务端 pull 增加**在途任务上限**（`max-inflight` 默认 1，见 3.3），派发节奏对齐串行打印；② Agent 端按 TaskId **入队去重**，拦截一切重复下发（paused 续打与异常救回两种情况放行）。残留风险：打印中断纸时已出纸的部分标签与续打的整份仍可能构成部分重复（取决于 BarTender/驱动行为），现场断纸时注意核对；Agent 端去重集合仅保留最近 10000 个 TaskId 且进程重启清空，极端情况下（单日超万任务且期间服务端重派数小时前的任务）去重可能失效，概率极低。
