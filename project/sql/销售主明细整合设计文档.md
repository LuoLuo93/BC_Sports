# 销售主明细整合设计文档

> 数仓 BI_DW(Oracle 19c @192.168.5.177:orcl),销售明细 ODS 层整合方案。

## 一、背景

销售数据分散在两类单据:POS **零售单**(伯俊 `M_RETAIL`/`M_RETAILITEM`)和**批发单**(伯俊 `M_SALE`/`M_SALEITEM`)。为做统一销售分析,将两张贴源表按统一结构合并为 `ODS_SALES_MAIN`,并在灌数时完成**小程序订单信息补齐**。2026-08 起新增**主播(ANCHOR)两列**,支撑直播带货销售分析,数据自零售单一路透传。

## 二、数据流

```
伯俊ERP生产库(10.0.1.22)
  │  Kettle 抽取(字段映射见 Kettle 作业)
  ├─ M_RETAIL/M_RETAILITEM 等 ──► ODS_RETAIL_DETAIL(32列, POS零售贴源)
  └─ M_SALE/M_SALEITEM 等    ──► ODS_SALE_DETAIL (30列, 批发贴源)
                                        │
              SP_FILL_ODS_SALES_MAIN(按 BILL_TIME 增量)
                                        ▼
                               ODS_SALES_MAIN(33列)
                                        ▲
  小程序订单 NX_TRADE_CUSTOMER_GUIDER_SHOP ─┘(③ MERGE 补齐会员/营业员/店铺)
  SP_UPDATE_NEW_OLD ──► 回填 NEW_OLD_NAME_ADJUST(见《新旧货分类设计文档.md》)
```

## 四、存储过程 SP_FILL_ODS_SALES_MAIN

**参数:** `P_START_TIME`, `P_END_TIME`(VARCHAR2,格式 `YYYY-MM-DD HH24:MI:SS`)— 按 **BILL_TIME(提交时间)** 的增量刷新范围。

**步骤:**
1. **幂等清理**:DELETE 范围内旧数据(按 BILL_TIME);
2. **灌数**:
   - ②-1 零售单:`ODS_RETAIL_DETAIL` → `ODS_SALES_MAIN`(RETAILITEM_ID→ITEM_ID,**主播两列透传**);
   - ②-2 批发单:`ODS_SALE_DETAIL` → `ODS_SALES_MAIN`(SALEITEM_ID→ITEM_ID,**主播两列灌 NULL**,源表无此列);
3. **小程序 MERGE**:`OMS_SOURCECODE = NX_TRADE_CUSTOMER_GUIDER_SHOP.OUT_TRADE_ID` 命中的行更新:
   - `SALES_TYPE = '小程序'`,`VIP_MOBILE = BIND_MOBILE`;
   - 营业员 = 导购(NX_YUN_EMPLOYEE.EMPLOYEE_NUM/NAME,按 SG_EXCLUSIVE_GUIDE_ID 关联);
   - 店铺 = 小程序店铺(NX_YUN_SHOP.OUT_ID/SHOP_NAME,按 SG_EXCLUSIVE_SHOP_ID 关联);**店铺关联不上 → STORE_CODE='BCHY',STORE_NAME='边城会员中心店'**;
   - 未匹配的订单保持原值;主播两列不被 MERGE 触碰。

**调用:**
```sql
EXEC SP_FILL_ODS_SALES_MAIN('2026-07-28 00:00:00', '2026-08-05 23:59:59');
```

## 五、关键技术点

1. **② 用 EXECUTE IMMEDIATE 动态 SQL**:绕过 PL/SQL 编译期 INSERT...SELECT 字符集推断(ORA-12704);
2. **MERGE 里 NVARCHAR2 字段用 TO_CHAR 转换**:避免 ORA-12704;
3. **参数用 VARCHAR2 + 固定掩码 TO_DATE**:避免 Kettle 调用时 NLS_DATE_FORMAT 隐式转换报 ORA-01861;
4. **幂等设计**:范围内 DELETE 再重灌,可安全重跑;重刷历史范围时,先重抽 ODS_RETAIL_DETAIL(带主播值)再跑本过程;
5. **加列安全性**:过程 INSERT 全部显式列名,`SP_UPDATE_NEW_OLD` 也只按列名 MERGE,ODS_SALES_MAIN 加列互不影响。
6. **索引与查询排序(2026-09-16)**:表上三个索引——`IDX_SALES_MAIN_EDITKEY(BILL_ID,ITEM_ID)` 供编辑 UPDATE 定位;`IDX_ODS_SALES_MAIN_TIME(BILL_TIME,BILL_NO)` 供列表日期范围查询/分页 COUNT/本过程按窗口 DELETE;`IDX_ODS_SALES_MAIN_BILLNO(BILL_NO)` 供单据号精确等值查询。**列表页 ORDER BY 必须与 TIME 索引列序完全一致**(`BILL_TIME DESC, BILL_NO DESC`),ROWNUM 分页才能走索引倒序 + STOPKEY 取前 N 行即停;换成其他排序列(如 ITEM_ID)会退化为 797 万行全表扫 + 全量排序(实测秒级 vs 对齐后 1~13ms)。

## 七、验证结果(2026-08-18)

- `ODS_RETAIL_DETAIL` / `ODS_SALES_MAIN` 主播两列均已就位,注释"主播ID/主播名称"无乱码;
- 过程重建后编译 VALID(无错误);
- 冒烟测试:重跑最近一小时窗口(2026-08-17 22:00~22:59,12 行),删了重灌行数前后一致(12=12);
- 依赖检查:该表唯一其他依赖 `SP_UPDATE_NEW_OLD` 只按列名 MERGE,不受加列影响。

## 八、变更记录 / 注意

1. **2026-08-18 新增主播两列并透传**:`ODS_RETAIL_DETAIL` 与 `ODS_SALES_MAIN` 各加 `ANCHOR_SUMMARYID`/`ANCHOR_SUMMARYNAME`(VARCHAR2(4000)),存储过程 ②-1 透传、②-2 灌 NULL。
2. **主播数据待补**:两列当前存量值均为 NULL——需先更新 Kettle 抽取字段映射把伯俊主播字段写进 `ODS_RETAIL_DETAIL`,再对相应时间段重跑 `SP_FILL_ODS_SALES_MAIN`。
3. **ODS_SALE_DETAIL 实为批发单**(列注释"批发单ID/批发单号"等);`sp_fill_ods_sales_main.sql` 过程内注释写的"销售退货单"系历史笔误,以库内注释为准。
4. 批发单天然无会员/网单号/操作人信息(对应列为 NULL),小程序 MERGE 也只命中 `OMS_SOURCECODE` 非空的零售单。
5. 部署含中文脚本必须 UTF-8 会话:`NLS_LANG=AMERICAN_AMERICA.AL32UTF8`(库字符集 AL32UTF8),否则中文常量乱码。
6. 下游新旧货分类回填见《新旧货分类设计文档.md》(回填 `NEW_OLD_NAME_ADJUST`,与本过程的增量范围参数机制一致)。
7. **2026-09-14 新增 TOT_AMT_ACTUAL(成交金额)/AMT_RECEIVABLE(应收金额)两列**(三张表同步加,NUMBER(28,10)),SP_FILL 已同步灌入;当时直接在库上加列,2026-09-16 补录进 `create_ods_sales_main.sql` 基线。
8. **2026-09-16 补建查询索引并修排序**:`IDX_ODS_SALES_MAIN_TIME(BILL_TIME,BILL_NO)` ONLINE 建成(此前缺失,分页/COUNT/ETL 删旧全表扫);列表页 ORDER BY 由 `BILL_TIME DESC, ITEM_ID DESC` 改为 `BILL_TIME DESC, BILL_NO DESC` 与索引对齐(见五-6);`TRANSACTION_AMOUNT` 页面展示名由"成交金额"改"实收金额",与新增两列区分。
9. **2026-09-16 单据号查询由前后模糊 LIKE 改为精确等值**:新增 `IDX_ODS_SALES_MAIN_BILLNO(BILL_NO)`(dw_sales_main_menu.sql 第 3 段,已在库执行);无日期范围的纯单号搜索实测全表扫 3~5s → 索引等值 65ms/分页 46ms/COUNT,前端提示改"请输入完整单据号";注意等值匹配区分大小写且不再支持片段模糊,需按单据原文完整输入。
